#* Knowledge base for Microcontroller hardware connection (mutable)
1. Hardware Bus Assumptions: Never assume standard I2C, SPI, or UART bus numbers (e.g., bus 0 or 1) translate directly to physical pins on non-mainstream/experimental SoCs. Always use terminal diagnostics (ls /dev/i2c*, i2cdetect -y [bus]) to verify the mapping before writing code.
2. Device Tree Overlay Naming: Generic overlay names (like i2c0 or gpio-ir) often fail on custom Linux builds. Do not guess overlay names. Inspect the compiled .dtbo files directly in the OS boot directory (e.g., /boot/dtb/.../overlay/) to find the exact prefix and naming convention required for the boot configuration file.
3. Hardware Permission Errors: If a Python script throws a PermissionError (Errno 13) on a /dev/ node, the code is likely fine. The issue is OS-level group permissions. Add the user to the respective hardware group (e.g., sudo usermod -aG i2c $USER). If the group does not exist, manually initialize it (sudo groupadd gpio) and assign persistent node ownership rules via a custom udev policy file under /etc/udev/rules.d/ to prevent reset across boots. Ensure sessions apply active groups via newgrp or a complete logout/login cycle.
4. GUI Config Limitations: TUI/GUI configuration tools (like armbian-config or raspi-config) often fail to map device trees for experimental boards. If an interface isn't listed in the UI, bypass it and manually append the correct overlay to the boot environment file (e.g., /boot/armbianEnv.txt).
5. I2C Kernel Reservations: When probing an I2C bus with i2cdetect, a UU indicator means the address is reserved and actively locked by a kernel driver (often internal PMIC or HDMI). Only explicit hexadecimal outputs (e.g., 3c) indicate available devices ready for user-space control.
6. User-Space GPIO Bias Rejection: When interacting with libgpiod in user-space on Allwinner/Sunxi-based kernels, passing software bias configurations (e.g., bias=Bias.PULL_DOWN) may cause a ValueError: (22, 'Invalid argument') if the underlying kernel driver does not expose physical pull-up/pull-down control registers to user-space. Bypass this restriction by identifying and targeting specific SoC pins that are hardware-wired with static internal pull-ups/pull-downs, and adjusting code logic to match (e.g., Active-Low scanning for native pull-up blocks).
7. Capacitive Noise Overriding: Mechanical matrix accessories connected via unshielded jumper wires are highly susceptible to capacitive ghosting or noise injections when touching nearby ground frames, chassis planes, or raw solder pads. Resolve this entirely in software by implementing multi-sample polling windows (e.g., requiring a pin state to remain consistent across 3 distinct samples over a 40–60ms window) rather than relying on standard single-delay debounce sweeps.
8. Kernel Enumeration Flipping: Linux does not guarantee the numerical order of device nodes (e.g., /dev/lirc0 vs. /dev/lirc1, or ttyUSB0 vs. ttyUSB1) across reboots due to driver initialization race conditions. Never hardcode node paths for identical subsystems. Instead, dynamically probe hardware capabilities at runtime (e.g., requesting driver feature flags or parsing /sys/class/) to route logic correctly.
9. Hardware Lock (Errno 16 'Device or resource busy'): If a user-space script throws this error when attempting to directly tap a raw GPIO pin, it means a kernel-space driver (e.g., gpio-ir-recv) has already successfully claimed and locked the pin. Do not attempt raw pin reads; interface with the translated kernel abstraction node instead.
10. EMI and CPU Scheduler Interference: During highly sensitive, time-critical hardware polling (like raw IR pulse space tracking), active Wi-Fi or Bluetooth radios can introduce massive electromagnetic interference (EMI) and steal CPU cycles. Temporarily block these radios using software switches (e.g., rfkill block) during the capture phase, and restore them afterward to ensure a clean signal reading.

#* Knowledge base for Python, AsyncIO & Strict Typing (mutable)
1. Strict Type-Hinting Defaults (Optional): When using strict linters (like Pylance/Pyright), assigning None as a default value to a strictly typed parameter (e.g., def func(payload: str = None)) triggers a type error. Always wrap the type in Optional from the typing module (e.g., payload: Optional[str] = None) to explicitly allow NoneType.
2. Type Narrowing: If a parameter is marked as Optional[str], passing it directly into a function that demands a strict str (like subprocess.exec) will throw an error. Use an if variable_name: block to trigger "Type Narrowing," proving to the linter that the variable is no longer None within that specific scope.
3. Strict Type Inference in Lists: Creating lists via comprehensions containing complex types (like lambda functions with specific keyword arguments) causes strict linters to rigidly lock the list's type signature. Attempting to .append() a slightly different function signature later will fail. Bypass this by explicitly declaring the variable as a generic list (items: list = []) before iterating and appending.
4. Dynamic Async Callbacks: Python lambda functions are inherently synchronous. You cannot directly await a lambda. If a UI or routing system needs to execute dynamic callbacks that might be asynchronous, you must execute the function synchronously first, capture the result, and check if asyncio.iscoroutine(result): before awaiting it.
5. Class Attribute Type Narrowing: Strict linters will not type-narrow instance attributes (e.g., `self.device_node`) even after an `if self.device_node:` check, because they assume asynchronous threads could modify the attribute between the check and execution. To satisfy the linter, assign the attribute to a local variable first (`local_node = self.device_node`), perform the `None` check, and pass the local variable forward.
6. Tuple Arity Mismatches: When refactoring layout engines or data pipelines to accept expanded structures (e.g., changing a 2-part tuple to a 3-part tuple), ensure all fallback applications and data sources are updated simultaneously. Passing a 2-part tuple to an engine unpacking three variables (`for a, b, c in list:`) causes an immediate and fatal `ValueError: not enough values to unpack`.
7. Duplicate Method Obscuration: Python evaluates classes top-to-bottom. If a class accidentally contains two methods with the exact same name (e.g., due to copy-pasting), the latter method silently overwrites the former without throwing a syntax error, leading to dead code and skipped lifecycle events.
8. Silent Subprocess Failures (stderr): Command-line tools routinely write fatal hardware errors or usage faults to standard error (`stderr`) while leaving standard output (`stdout`) empty. When using `asyncio.create_subprocess_exec`, always capture, decode, and explicitly evaluate `stderr` if the process fails or returns empty, to prevent the application from silently swallowing hardware faults.

#* Knowledge base for UI Architecture & State Routing (mutable)
1. Zombie Async Tasks (Memory Leaks): Background `asyncio` loops tied to UI components (like blinking cursors, telemetry, or animations) continue to execute even when the UI component is suspended or pushed to the background. Always bind these tasks to instance variables and explicitly `.cancel()` them during the component's `on_stop`/teardown phase, and wrap their drawing execution in a strict "is active" state check (`if os.current_app is self:`).
2. Stateful UI Caching Collisions: When using a UI router that caches suspended views in memory to speed up switching, dynamically generated modals or popups sharing the same string ID (e.g., 'modal_view') will collide. The router will wake up the stale cached instance (a "ghost app") instead of mounting the new one. Always implement a cache-overwrite mechanism (e.g., passing a `fallback_app` instance) or uniquely ID dynamic views.
3. Dangling Render States: If a floating child modal modifies or injects drawing instructions into a suspended parent app's layout canvas, it must explicitly erase those instructions before triggering its own teardown/callback. Otherwise, when the parent app wakes up, it will redraw the "dead" child's UI artifacts.
