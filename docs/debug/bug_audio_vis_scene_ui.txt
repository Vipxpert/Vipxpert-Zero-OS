# Stage: Isolation & Telemetry Plan
1. DPR-348 + PR-352 + P-355 findings: When `5002000.i2c` is rebound cleanly, `0x4C` and `0x43` (`BusV=4.040V`) respond 100% cleanly! However, at boot (`t=0s`), `OSKernel.recover_i2c0_bus()` writes `0x01` to `TWI0_SRST` (`0x1C`), leaving `TWI0_STAT` (`0x10`) at `0x00` (and clearing `TWI0_CNTR` `TWSIEN` bits behind `mv64xxx_i2c`'s back). Then at `t=2.0s`, `UIManager._apply_pcm5122_i2c_gain()` checks `if twi_m[0x10] in (0x00, 0x38): twi_m[0x1C:0x20] = 0x01`, wiping `TWI0_CNTR` right as `PowerMonitor` addresses `0x43` (`state: 0x2, status: 0x0` -> `Errno 11`), and `UIManager._check_and_heal_pcm5122()` repeats this every 3s because `twi_m[0x10] == 0x00`!
2. DPR-361..DPR-372 + CDR-375 Fix Applied & User-Verified ("Seems worked", LIVE DB `4.060|0.2|86.00`, 0 I2C0 faults/stutters):
   - Proven dual root cause: (a) `PowerMonitor` held `I2C_BUS_LOCK` across `time.sleep(0.145)` (`179ms` freeze in DPR-372) and relied on `shm[12:16]=1` (which `Display.show()` overwrote after `31ms` in DPR-361), causing `0x43` vs `0x3C` collisions (`STAT=0xF9`/`0x38`, `Errno 11`); (b) `UIManager._check_and_heal_pcm5122()` treated `STAT==0x00`/`0x38` as a fault every 3s and fired `_apply_pcm5122_i2c_gain(pulse_standby=True)` (`Reg 0x02=0x11` mute + `0x4D` NACK + `TWI0_SRST`), causing a repeating 3-second UI scroll + audio stutter loop across every screen.
   - Fixed in `CDR-375` (`power_monitor.py`, `ui_manager.py`): moved `time.sleep(0.145)` outside `I2C_BUS_LOCK` (`<1.2ms` 100kHz-scoped bursts), removed `shm[12:16]` writes from `PowerMonitor`/`UIManager`, restricted `_check_and_heal_pcm5122` strictly to `shm[32:36]` pin-reset counter changes with `pulse_standby=False`, and deleted temporary `/tests/diag_ina219_i2c0.py`.
